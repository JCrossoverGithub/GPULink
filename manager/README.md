## Run with an existing local Core installation

On Linux/WSL with Node 24, start the selected Core installation by its existing managed CLI workflow, then run:

```
node manager/gateway.mjs --config-dir /absolute/path/to/installation
```

Open the exact printed `http://127.0.0.1:PORT/` address. Ctrl+C closes the manager only. The preview accepts the generated private `admin.env` and `client.env` profiles for `http://127.0.0.1:8088`, read under the current user's ownership and POSIX permissions. The Core listener must be trusted and already running; the manager neither starts it nor verifies its process identity. No credentials are passed to the browser. No LAN bind, reverse proxy, external assets, arbitrary upstream URL, raw upstream error, or write route. This is a local operator trust boundary, not multi-user authentication: other trusted local processes can access the manager. Do not expose it to a network. Metadata displayed from Core is operational data and may itself be sensitive.

## Data contract and limitations

- Manager requires matching updated Core. The admin-only `GET /v1/admin/operational-snapshot` returns schema 2: one consistent database observation including worker inventory, all active jobs and occupying sessions, all non-clear scheduler fences, job cleanup holds and recent event headers. No scheduler pass or release occurs. SQLite uses the existing serialized `BEGIN IMMEDIATE` transaction; PostgreSQL uses a separate read-only repeatable-read transaction without fence row or advisory locks. The normal placement fence query still locks rows. No schema migration is required.
- The snapshot includes up to 500 recent and 500 queued/requested records per workload kind plus every active allocation. At-limit truncation is detected with one extra row, not guessed. Events contain the latest 200 retained headers (sequence, type, subject ID, time), newest first; the API never returns event payloads. The UI refreshes with the snapshot on change notifications and through five-second fallback polling. This is a bounded recent timeline, not a lossless audit log. Reconnection replaces the snapshot rather than replaying browser state. Historical browsing remains a separate future slice.
- Core derives device state from the same occupancy and fence identities used by the scheduler. Active allocations and job cleanup holds block a UUID across registrations. Other fences block the worker/UUID pair. Device state distinguishes allocation, job cleanup hold, other safety fence, offline, stale heartbeat, drain and unallocated. Multiple registrations are still reported as such, not guaranteed distinct physical devices. An unallocated device is not necessarily eligible for a given workload; no per-workload placement evaluation is claimed. Telemetry is hidden outside the configured heartbeat freshness window, on offline workers or when disconnected. The last valid snapshot is retained on failure.
- Explicit field projection excludes payloads, results, raw error details, session metadata, lease identifiers, worker labels and URLs. Gateway independently reprojects the response. This is not arbitrary-content redaction: operator-provided names and identifiers may be sensitive. Existing Core event SSE is unchanged.
- The gateway makes one fixed authenticated Core GET with a four-second deadline, 8 MiB response bound, redirect refusal and no browser credential. Successful requests coalesce/cache for one second unless invalidated by a change notification. Snapshot projections reject over-limit worker, job, session or fence lists rather than silently dropping active work. Large-cluster performance, including SQLite writer-lock duration and PostgreSQL read workload, is not yet measured. The loopback gateway and read-only security boundary remain unchanged. No mutation routes, lifecycle authority or recovery controls.
- C+ CSS, approved offline design and title are unchanged. Existing dashboard remains intact. No new runtime dependencies. Queue explanations, full event replay, historical telemetry, controls, distribution and physical acceptance remain outstanding.

## DEV-07B2B — event-driven refresh

The manager still derives all displayed operational state from schema 2 snapshots. The new admin-only `/v1/admin/operational-changes` SSE channel uses the existing committed-event subscription (including PostgreSQL LISTEN/NOTIFY). It does not read, replay, or transmit event records. The channel sends only fixed `ready`, `changed`, and `heartbeat` frames. Changes are coalesced within one second, there are at most 32 subscribers per Core, heartbeats are sent every ten seconds, and slow or disconnected consumers are removed. The original `/v1/events` contract is unchanged. The route is unavailable until event notifications are started.

The localhost gateway shares one authenticated upstream stream across all its browser subscribers and stops it when the last tab leaves. It accepts only fixed frames, refuses redirects and oversized/malformed frames, retries after two seconds, and times out an idle upstream after 25 seconds. Browser `/api/changes` requires same-origin fetch metadata or the explicit local API header, with the existing host/origin and read-only checks. The browser receives only constant notifications, never upstream credentials or bytes. Gateway invalidation discards the one-second cache; reads already in flight cannot repopulate an invalidated cache. On reconnect, an initial notification requests a new snapshot, including recent event headers that changed while disconnected. Already in-flight reads may still return their consistent older observation; subsequent refreshes reconcile it.

The browser uses a single-flight refresh controller, at least one second between request starts, a trailing refresh for changes arriving during a read, and five-second polling after each completed request even while SSE is healthy. Settings and Events show notification delivery separately from snapshot health. Ordinary telemetry updates and clock-based staleness need not emit an event, so polling remains required. Snapshot errors retain the last valid sample and mark it stale; notification failure alone does not invalidate successfully polled state. The recent event timeline is still bounded to 200 distinct ordered headers; there is no lossless replay or historical audit claim. No scheduling changes, mutation routes, database migrations or dependencies were introduced. The C+ stylesheet, frozen design archive and title remain intact; the live HTML script is now a browser module.

QA: `node --test test/manager-changes.test.mjs test/manager-readonly.test.mjs`. The fixture can accept `event` and `disconnect` on stdin with `--qa-disconnect`. The optional browser check validates notification-driven refresh and stale retention; `--offline-render` explicitly substitutes browser transport while retrieving actual gateway snapshots. A separate real HTTP test covers the actual SSE transport, burst coalescing, shared upstream, rollback, invalid frame refusal, reconnect and cache invalidation during an in-flight request. A cross-instance PostgreSQL test is included in the existing disposable job-cleanup CI job. No live PostgreSQL service or Node 24 was available in the sandbox; direct Chromium localhost navigation is blocked by its administrator policy. Large-cluster load and latency remain unmeasured.

## DEV-07C — operational views

The approved C+ navigation, device modules, palette, and optional inspector/tree are retained. Job and session registers now filter all/active/pending/terminal records within the existing bounded snapshot, and search matches worker/device names as well as identifiers. Event history offers worker/job/session/other filtering, readable names for known event types, raw type labels for diagnostics, full timestamps, and descriptive resource links. Unknown types are displayed literally, not interpreted as commands or object properties. Worker inspection includes capabilities, active workloads and recent worker events. Device inspection links active allocations, known holds and worker capabilities; job/session inspection includes recorded placement, attempt or interruption count and recent lifecycle events. Matching reported adapters are capability matches only; actual implementation choice and per-workload eligibility are not claimed. Adapter details show reported readiness, check time, schema and reporting worker devices. Recovery inspection shows the original worker, affected registrations, associated job and existing operator recovery requirements; no action releases a hold. Identifiers remain accessible in expandable diagnostics. Inspector Back navigation is bounded to 32 prior records. Topology shows at most four hosts per page, preserving logical graph connectivity; rack and table remain available. The workspace stays top-aligned with a tall inspector. All UI data remains the existing schema 2 snapshot, with no Core/gateway/transport/schema/dependency changes. Historical telemetry, full event replay, authoritative queue explanations, mutation routes, package integration and physical acceptance remain deferred.
