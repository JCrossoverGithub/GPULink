# GPULink Manager

C+ is the approved visual direction. `design/CPlus.html` is the exact approved offline design source (SHA-256 f19cc5cb937fec7fb954005f09920df693c54124c4e3d746280368eaeaa0f71e). It is NOT served by the live gateway. The implementation retains the industrial styles, rack/table/topology, resource tree and non-modal inspector. The shipped live view has no simulated operation or fallback records. The live Manager is included in the private CLI distribution candidate.

## Run with an existing local Core installation

On Linux/WSL with Node 24, start the selected Core installation by its existing managed CLI workflow, then run:

```
gpulink --config-dir /absolute/path/to/installation manager
```

Open the exact printed `http://127.0.0.1:PORT/` address. The launcher attempts to open the browser on a graphical Linux or WSL desktop, prints the URL in every case, and supports `--no-open`. Ctrl+C closes Manager only; the selected Core and workers remain running. The launcher verifies the private generated profiles and the existing local supervisor's installation-bound process identity before contacting Core; every fresh upstream snapshot, mutation and notification connection rechecks readiness/ownership. This is not an atomic binding of the HTTP socket to the supervisor, and other trusted local processes are within the trust boundary. The gateway never starts or adopts an unrelated control plane. No Core credentials are sent to the browser. No LAN bind, reverse proxy, external assets, arbitrary upstream URL, or raw upstream errors. Metadata displayed from Core may be sensitive. Read-only is the default; `--enable-controls` is an explicit local operator opt-in. Native Windows managed services, remote browser administration and multi-user authentication are not supported. If both default local and server profiles exist, use `--config-dir` to select one; custom directories are never discovered automatically. A source checkout can use `npm run cli -- --config-dir DIRECTORY manager` for contributor development. The old standalone gateway command now directs callers to this verified CLI launcher.

## Data contract and limitations

- Manager requires matching updated Core. The admin-only `GET /v1/admin/operational-snapshot` returns schema 2: one consistent database observation including worker inventory, all active jobs and occupying sessions, all non-clear scheduler fences, job cleanup holds and recent event headers. No scheduler pass or release occurs. SQLite uses the existing serialized `BEGIN IMMEDIATE` transaction; PostgreSQL uses a separate read-only repeatable-read transaction without fence row or advisory locks. The normal placement fence query still locks rows. No schema migration is required.
- The snapshot includes up to 500 recent and 500 queued/requested records per workload kind plus every active allocation. At-limit truncation is detected with one extra row, not guessed. Events contain the latest 200 retained headers (sequence, type, subject ID, time), newest first; the API never returns event payloads. The UI refreshes with the snapshot on change notifications and through five-second fallback polling. This is a bounded recent timeline, not a lossless audit log. Reconnection replaces the snapshot rather than replaying browser state. Historical browsing remains a separate future slice.
- Core derives device state from the same occupancy and fence identities used by the scheduler. Active allocations and job cleanup holds block a UUID across registrations. Other fences block the worker/UUID pair. Device state distinguishes allocation, job cleanup hold, other safety fence, offline, stale heartbeat, drain and unallocated. Multiple registrations are still reported as such, not guaranteed distinct physical devices. An unallocated device is not necessarily eligible for a given workload; no per-workload placement evaluation is claimed. Telemetry is hidden outside the configured heartbeat freshness window, on offline workers or when disconnected. The last valid snapshot is retained on failure.
- Explicit field projection excludes payloads, results, raw error details, session metadata, lease identifiers, raw worker label maps and URLs. The explicitly reserved, validated `gpulink.display-name` label alone may appear as optional `displayName`. Gateway independently reprojects the response. This is not arbitrary-content redaction: operator-provided names and identifiers may be sensitive. Existing Core event SSE is unchanged.
- The gateway makes one fixed authenticated Core GET with a four-second deadline, 8 MiB response bound, redirect refusal and no browser credential. Successful requests coalesce/cache for one second unless invalidated by a change notification. Snapshot projections reject over-limit worker, job, session or fence lists rather than silently dropping active work. Large-cluster performance, including SQLite writer-lock duration and PostgreSQL read workload, is not yet measured. The loopback gateway and read-only security boundary remain unchanged. No mutation routes, lifecycle authority or recovery controls.
- C+ CSS, approved offline design and title are unchanged. Existing dashboard remains intact. No new runtime dependencies. Queue explanations, full event replay, historical telemetry, controls, distribution and physical acceptance remain outstanding.

## DEV-07B2B — event-driven refresh

The manager still derives all displayed operational state from schema 2 snapshots. The new admin-only `/v1/admin/operational-changes` SSE channel uses the existing committed-event subscription (including PostgreSQL LISTEN/NOTIFY). It does not read, replay, or transmit event records. The channel sends only fixed `ready`, `changed`, and `heartbeat` frames. Changes are coalesced within one second, there are at most 32 subscribers per Core, heartbeats are sent every ten seconds, and slow or disconnected consumers are removed. The original `/v1/events` contract is unchanged. The route is unavailable until event notifications are started.

The localhost gateway shares one authenticated upstream stream across all its browser subscribers and stops it when the last tab leaves. It accepts only fixed frames, refuses redirects and oversized/malformed frames, retries after two seconds, and times out an idle upstream after 25 seconds. Browser `/api/changes` requires same-origin fetch metadata or the explicit local API header, with the existing host/origin and read-only checks. The browser receives only constant notifications, never upstream credentials or bytes. Gateway invalidation discards the one-second cache; reads already in flight cannot repopulate an invalidated cache. On reconnect, an initial notification requests a new snapshot, including recent event headers that changed while disconnected. Already in-flight reads may still return their consistent older observation; subsequent refreshes reconcile it.

The browser uses a single-flight refresh controller, at least one second between request starts, a trailing refresh for changes arriving during a read, and five-second polling after each completed request even while SSE is healthy. Settings and Events show notification delivery separately from snapshot health. Ordinary telemetry updates and clock-based staleness need not emit an event, so polling remains required. Snapshot errors retain the last valid sample and mark it stale; notification failure alone does not invalidate successfully polled state. The recent event timeline is still bounded to 200 distinct ordered headers; there is no lossless replay or historical audit claim. No scheduling changes, mutation routes, database migrations or dependencies were introduced. The C+ stylesheet, frozen design archive and title remain intact; the live HTML script is now a browser module.

QA: `node --test test/manager-changes.test.mjs test/manager-readonly.test.mjs`. The fixture can accept `event` and `disconnect` on stdin with `--qa-disconnect`. The optional browser check validates notification-driven refresh and stale retention; `--offline-render` explicitly substitutes browser transport while retrieving actual gateway snapshots. A separate real HTTP test covers the actual SSE transport, burst coalescing, shared upstream, rollback, invalid frame refusal, reconnect and cache invalidation during an in-flight request. A cross-instance PostgreSQL test is included in the existing disposable job-cleanup CI job. No live PostgreSQL service or Node 24 was available in the sandbox; direct Chromium localhost navigation is blocked by its administrator policy. Large-cluster load and latency remain unmeasured.

## DEV-07D1 — opt-in local operations

The default gateway remains read-only. To intentionally enable the four local management controls, use `gpulink --config-dir DIRECTORY manager --enable-controls`. This is a trusted local-operator preview; it is **not** multi-user authentication or network-facing administration. Other trusted local processes can access the loopback gateway. Do not expose it through a reverse proxy or LAN binding. A per-process random anti-CSRF token is delivered only in the same-origin snapshot in operator mode (not a Core credential or authentication against local processes). A POST requires the exact Host and Origin, same-origin fetch metadata, that token, and a bounded JSON body. The gateway admits one mutation at a time across its tabs. Only four fixed actions are accepted; no browser-supplied route, upstream URL, arbitrary payload, lease, or credential is used. Core admin credentials are used for drain/resume and client credentials for cancel/close, as required by the existing Core routes. No raw Core response, payload or error text is returned to the browser.

Each action requires confirmation of the logical record identity and displayed state. The gateway obtains a fresh authoritative snapshot before dispatch and refuses missing or changed records. This is not a transactional compare-and-set: another Core client may change state between the preflight and mutation; Core remains responsible for transition arbitration. Actions target logical jobs/sessions, not individual lease attempts or processes. A successful response must identify the expected record and resulting state. A rejected preflight sends no mutation. Network failures, unexpected responses and server errors after dispatch are treated as uncertain, with no automatic mutation retry. The UI refreshes authoritative state after any result, retains the outcome notice and disables controls while stale or in progress. Acknowledgement is not proof of process exit or GPU cleanup. Running batch cancellation still uses the existing durable hold behavior; session closure follows existing Core semantics and does not certify host process cleanup. No worker enrollment, process stop/start or fence-release operation is exposed. Recovery remains inspection-only.

Disposable operator preview: `node manager/qa/preview-fixture.mjs --enable-controls --qa-disconnect`. It adds an intentionally unschedulable queued job (`qa-cancel-demo`) so cancellation can be exercised in addition to the existing cancelled job/hold and allocated session. The fixture is synthetic, isolated and uses no physical GPU. Run `node --test --test-concurrency=1 test/manager-operations.test.mjs test/manager-readonly.test.mjs test/manager-changes.test.mjs`. Optional `python manager/qa/operations_browser_check.py` exercises browser operations; `--offline-bridge` substitutes browser fetch with a Python QA bridge that calls the actual fixture gateway and supplies browser request metadata. The latter was used in the sandbox; native browser-origin transport and Node 24 CI remain outstanding. Existing read-only browser QA also passes using `--offline-render`. Twelve targeted Node 22 tests passed (including real SQLite/Core lifecycle, cross-origin refusal, malformed/uncertain acknowledgement, serialization, read-only default, cancellation hold and stale rejection). No Core code, scheduler, database schema, package dependencies or accepted C+ design archive changed. No PostgreSQL or physical GPU test was run for this slice. GPU recovery, distribution and physical acceptance remain future work.

## DEV-07D2 — guarded job cleanup hold recovery

Read-only remains the default. With `--enable-controls`, Recovery exposes an action only for an exact job cleanup hold, not broker-owned or other scheduler fences. The inspector requires the original worker to be reported offline and drained, a fresh snapshot, and no active job/session allocation on that UUID. These are preliminary checks, not a cleanup certificate. The confirmation requires independent physical cleanup attestation and typing the exact GPU UUID. Closing the dialog sends no request. The operator must verify that the original execution and its child processes have stopped before attesting; the Manager cannot perform that verification.

The gateway accepts only the explicit recovery request shape, applies existing same-origin, CSRF, size and serialized-operation controls, reads a fresh operational snapshot, then reads the existing admin-only hold list to resolve the exact lease ID. The lease is never sent to the browser. Core atomically verifies worker/UUID/job/lease/epoch, terminal ownership, offline/drained state, and absence of active allocations or open execution attempts. Only `released:true, operatorAttested:true` is accepted as acknowledgement. Conflicts refuse release, uncertain results are not retried, and the refreshed snapshot and existing `job.cleanup_operator_confirmed` event are authoritative. The worker remains drained; release does not resume it or prove physical cleanup. No Core or schema changes are introduced. Other fences remain read-only.

Disposable recovery preview: `node manager/qa/preview-fixture.mjs --enable-controls --qa-recovery --qa-disconnect`. This dedicated scenario advances the synthetic clock and marks the original worker drained/offline; no physical worker or GPU process exists. Use only this fixture for simulated attestation. Optional `python manager/qa/recovery_browser_check.py` exercises direct browser HTTP (or `--offline-bridge` for sandbox-only transport substitution). Existing Manager and cleanup hold regression tests remain applicable.

## Optional worker display names

The CLI `join` and `worker enroll` accept `--name NAME` for a public operator label. The registration name and local ownership key remain random and unchanged. Duplicate display names are distinguished by a short registration reference (full reference if the short references collide). Legacy generated names are compacted in Manager; exact registration names and worker IDs remain visible in technical identifiers and mutation confirmation. Other worker names are preserved. The label is presentation metadata, not proof of machine identity, scheduling authorization, or per-worker revocation. No rename action is exposed. Joining alone does not register a worker; the empty cluster explains the explicit start step.
